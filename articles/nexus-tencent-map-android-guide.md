# uni-app x 接腾讯地图：Android 原生配置与导航事件怎么验收

做地图页面时，最容易误判的环节是把“地图显示出来”“算路成功”和“导航开始”当成同一件事。实际接入中，建议把这三步拆开测试，每一步都保留能对应到当前实例的证据。

本文以 `nexus-tencent-map` 为例，整理 Android 接入的检查顺序。公开的 1.0.1 验证记录覆盖 Android 独立 Native 宿主中的地图、服务器驾车算路和模拟导航；UTS/uvue 真机在线流程、iOS 设备与 GPS 导航尚未完成验收。[插件说明与验证记录](https://ext.dcloud.net.cn/plugin?id=30642)

## 1. 先写清楚自己的运行环境

排查前，建议在问题记录中写清这几项：

- HBuilderX 版本，以及使用 uni-app 还是 uni-app x。
- 页面类型与组件模式。
- 手机型号、系统版本，以及安装包的构建时间。
- 当前是在验证编译、地图显示、路线规划，还是导航过程。

“编译通过”和“手机上完整跑通”应该是两条记录。这样遇到问题时，才能分清是在构建配置、原生依赖、服务鉴权，还是页面调用顺序上。

## 2. 检查三个容易遗漏的接入点

### Key 要同时检查宿主配置与初始化

公开说明要求 Android 宿主配置 `TencentMapSDK` 元数据，并在初始化时传入一致的 Key。只在演示页面填写 Key，不能替代宿主原生配置。[Android 配置说明](https://ext.dcloud.net.cn/plugin?id=30642)

建议把配置核对放在第一次打包前。不要在公开问题单、截图或日志中粘贴真实凭据；需要协作排查时，分享占位模板和配置位置即可。

### 修改原生依赖后，要验证新安装包

1.0.1 补齐了导航布局使用的 `RecyclerView 1.3.2`，更新后需要重新制作自定义基座或原生安装包。[版本更新记录](https://ext.dcloud.net.cn/plugin?id=30642)

复验时建议先确认手机安装的确实是新包。只看页面上的版本文字，未必能判断原生构建是否更新。把构建时间和安装步骤记下来，可以减少“代码改了，设备结果没变”的重复排查。

### 路线 ID 与导航会话 ID 要分开处理

开始导航使用规划结果中的 `routes[n].routeId`。Android 驾车数据就绪事件中的 `navSessionId` 用于匹配导航会话，不能拿来替代路线 ID。[参数与事件说明](https://ext.dcloud.net.cn/plugin?id=30642)

建议给这两类标识使用不同的变量名和日志字段。页面切换、重新算路或重建实例后，也要确认后续操作使用的是当前实例的数据，避免旧结果混入新流程。

## 3. 用一条最小流程做验收

下面是建议的项目验收方法，不是新增的测试结果：

1. 先按项目的隐私交互和文档要求完成初始化，记录成功或失败的实际结果。
2. 只测试一个地图实例，确认视图加载与错误处理。
3. 使用固定测试起终点发起驾车算路，记录返回结果，不手工拼造路线标识。
4. 从当前返回的路线中选择一条，测试模拟导航，并观察实际状态变化。
5. 测试停止、离开页面和重新进入，确认页面状态与底层状态能对应。
6. 最后再加入业务表单、订单状态或其他页面逻辑。

每次测试建议保留四类证据：运行环境、操作顺序、关键事件和截图。截图说明应写清是否为固定示例坐标、是否使用模拟导航，让其他开发者能够理解它证明了什么。

## 4. 给失败路径留出位置

项目验收可以另外安排一轮失败场景：配置不正确、网络不可用、请求没有返回可用路线，以及用户主动停止操作。

这轮检查的目标是确认页面不会停留在虚假的成功状态。错误信息要能帮助用户重试或退出，也要能让开发者定位到具体步骤。

如果你正在评估 uni-app x 中的腾讯地图接入，可以先按上述顺序验证自己的目标环境，再决定如何接入业务。组件范围、完整参数和当前验收记录以 [nexus-tencent-map 的 DCloud 页面](https://ext.dcloud.net.cn/plugin?id=30642)为准。
